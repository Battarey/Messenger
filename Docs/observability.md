# Наблюдаемость (Observability) и Логирование

## 1. Стек Наблюдаемости

Для мониторинга и отладки распределенной системы используется следующий стек:
* **Логирование:** `Grafana Loki` + `Promtail`. Микросервисы пишут логи исключительно в `stdout/stderr` (в формате JSON). Установленный в системе агент `Promtail` автоматически собирает логи всех Docker-контейнеров и отправляет их в централизованное хранилище `Loki`.
* **Метрики:** `Prometheus` (сбор метрик производительности и бизнес-метрик с эндпоинтов `/metrics` микросервисов).
* **Трассировка:** `OpenTelemetry` (для отслеживания пути прохождения распределенных запросов между сервисами).

---

## 2. Стандарты логирования

Все микросервисы должны следовать единому стандарту логирования:
1. **Запись в stdout:** Запрещается записывать логи в файлы на диск контейнеров. Это замедляет работу и усложняет сбор логов.
2. **Структурированный формат (JSON):** В продакшен-окружении (`ENV=production`) логи должны выводиться в формате JSON. Это позволяет `Loki` индексировать метаданные (например, `service_name`, `request_id`, `user_id`) для быстрой фильтрации.
3. **Наличие Request ID:** Каждому входящему HTTP/WebSocket запросу на шлюзе (Gateway) присваивается уникальный заголовок `X-Request-ID`. Этот ID должен пробрасываться через все микросервисы и добавляться в контекст каждого лога.

## 3. Уровни логирования (LOG_LEVEL)

Выбор уровня лога должен строго соответствовать следующим критериям:

### `DEBUG` (Отладка)
Используется только для локальной разработки и детальной диагностики проблем.
* **Что логировать:** Сырые SQL-запросы (без паролей), заголовки HTTP-запросов, инициация WebSocket-соединений, детальные шаги выполнения сложных алгоритмов.
* **Внимание:** В продакшене этот уровень должен быть выключен для экономии дискового пространства и снижения нагрузки на сеть.

### `INFO` (Информация)
Стандартный уровень для отслеживания нормального жизненного цикла приложения.
* **Что логировать:** Успешный старт/остановка сервиса, применение миграций БД, успешная авторизация пользователя (без токена), создание чата.

### `WARNING` (Предупреждение)
Используется для фиксации аномалий, которые не ломают работу приложения, но требуют внимания.
* **Что логировать:** Медленные запросы к БД (превышающие лимит времени), кратковременные таймауты при обращении к внешним API (с успешным повтором), попытки несанкционированного доступа с неверными токенами.

### `ERROR` (Ошибка)
Используется для фиксации сбоев, требующих оперативного вмешательства разработчиков или администраторов.
* **Что логировать:** Необработанные исключения (unhandled exceptions), сбои подключения к базе данных или Redis, ошибки отправки уведомлений.
* **Правило:** К логам уровня `ERROR` обязательно должна прикрепляться трассировка стека (stack trace) ошибки.

## 4. Безопасность и конфиденциальность (PII)

> [!CAUTION]
> **Категорически запрещается** записывать в логи конфиденциальную информацию пользователей (Personal Identifiable Information - PII) и секреты авторизации.

**Что никогда не должно попадать в логи:**
* Пароли пользователей (в любом виде, даже захешированные).
* Токены авторизации (`Access JWT`, `Refresh JWT`).
* Одноразовые коды подтверждения регистрации (`OTP-коды`) в режиме `production` (в режиме `development` вывод в лог воркера разрешен для удобства локального тестирования).
* Личные сообщения пользователей и вложения.
* Номера телефонов, адреса и другие персональные данные, если они не замаскированы.
